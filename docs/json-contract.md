# JSON contract, version 1.1.0

The authoritative shape is [report.schema.json](report.schema.json), generated from the public Pydantic `Report` model. The [demo JSON](../examples/demo-report.json) is generated by the CLI from fictional data. JSON is UTF-8, uses explicit nulls for unknown observations, and has no terminal formatting or progress messages on stdout.

| Field | Semantics |
| --- | --- |
| schema_version | Contract version, currently the literal `1.1.0`. |
| tool_version | Software version, independent of the schema version. |
| generated_at | ISO 8601 timestamp with UTC offset. Demo uses a documented fixed fixture clock. |
| mode | `live` or `demo`; dashboards must visibly distinguish them. |
| status | `complete` or `incomplete`. Complete means the implemented collection calls finished, not that all AWS risks are covered. |
| accounts | Account IDs, per-account status, and collected user, role, and local/inline policy counts. Duplicate target accounts are collected once. |
| summary.active | Number of unsuppressed findings. |
| summary.suppressed | Number of matched suppression records, counted once per finding. |
| summary.by_severity | Active finding counts, with all four severity keys present, including zeros. |
| findings | Active findings, sorted by critical, high, medium, low, then account ID and finding ID. |
| suppressed_findings | Findings with a non-null suppression_reason, in the same priority order. |
| collection_issues | Account, resource, operation, and error code. Raw SDK error messages and credentials are excluded. |

Each finding has `id`, `rule_id`, `severity`, `account_id`, `resource`, `title`, `evidence`, `remediation`, and `suppression_reason`. Severity is exactly `critical`, `high`, `medium`, or `low`. Rule IDs `IAM001` through `IAM007` are stable. Resources are IAM ARNs, with `#inline/policy-name` appended for inline policies. Key findings identify the owning user and include only a key suffix and SHA-256 fingerprint, not a complete key ID or secret.

`id` is the first 24 hexadecimal characters of SHA-256 over NUL-separated rule ID, account ID, resource, and a rule-specific subject. Subjects are service namespace for IAM001, key fingerprint for IAM002, statement index for policy and trust statements, policy ARN for AdministratorAccess attachments, and empty for identity-level rules. IDs exclude mutable timestamps and severity. Reordering policy statements changes their IDs; they are correlation keys, not permanent global vulnerability identifiers.

`evidence` is a JSON object. The schema deliberately allows rule-specific JSON values. Dashboards must display unknown evidence keys generically and tolerate missing keys when comparing versions; do not parse the prose title or remediation. Null timestamps mean absent observations, not zero days. There is no computed universal account risk score.

Within 1.x, existing fields and enum meanings remain compatible. New optional fields may be added with a schema minor version. Required-field removal, type changes, severity/rule enum changes, or finding-ID changes require a major version. Consumers should validate the supported schema version, ignore unknown optional fields when their validator allows it, and reject unsupported major versions.

An incomplete account may still contain valid positive findings. A dashboard must retain those findings and display missing coverage, even if active is zero. Suppression never repairs missing collection, and its reason is an exception record rather than evidence that a risk is fixed.

Version 1.1.0 adds finding classification and IAM008/IAM009 rule identifiers. No finding asserts validated effective permission. Boundary ARNs, where present, are evidence context only.
